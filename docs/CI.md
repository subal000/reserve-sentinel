# Running Unwind unattended

Two GitHub Actions workflows keep Unwind's core claim ("we measure this
continuously") actually true instead of aspirational:

- **`.github/workflows/score.yml`** — every 15 minutes, reads live market
  data and writes fresh scores to the devnet program.
- **`.github/workflows/snapshot.yml`** — twice a day (05:30 and 15:00 UTC),
  runs the cross-lender exit-depth study and commits the result as a dated
  folder under `research/2026-09-16-cross-lender-exit/snapshots/`.

Both are free: GitHub gives public repos unlimited Actions minutes.

## One-time setup

### 1. Split the score-writer key from the program-upgrade key

**Do this before adding any secret to GitHub.** Today the same keypair
(`~/.config/solana/id.json`, pubkey `4iSkR32hGhGAV5aNojWh4kZsCTbLm5KctsTvFTYLW18e`)
can both write scores *and* upgrade the deployed program. Only the first
capability needs to leave your machine; the second must not.

```bash
# Generate a dedicated upgrade-only keypair (stays local, never committed,
# never pasted into a GitHub secret).
solana-keygen new --no-bip39-passphrase -o ~/.config/solana/unwind-upgrade.json

# Move the program's upgrade authority to it.
solana program set-upgrade-authority BVkkMMqDuFRgzNtwy9Uc87cJu574YDU6j4us9i7EYMba \
  --new-upgrade-authority "$(solana-keygen pubkey ~/.config/solana/unwind-upgrade.json)" \
  --keypair ~/.config/solana/id.json --url devnet

# Verify — the Authority line should now show the NEW pubkey, not 4iSkR3...
solana program show BVkkMMqDuFRgzNtwy9Uc87cJu574YDU6j4us9i7EYMba --url devnet
```

After this, `id.json` can only call `update_score` (the instruction the
indexer uses) — it can no longer replace the program's code. That's the
right blast radius for a key that's about to sit in GitHub's secret store.

Back up `~/.config/solana/unwind-upgrade.json` somewhere safe (a password
manager, an encrypted drive). If you lose it with no upgrade authority set
elsewhere, the program can never be upgraded again.

### 2. Add repo secrets

Settings → Secrets and variables → Actions → New repository secret.

| Secret | Value | Required |
|---|---|---|
| `AUTHORITY_KEYPAIR_JSON` | `cat ~/.config/solana/id.json` — paste the whole JSON array | yes |
| `PYTH_PRO_API_KEY` | from `.env` | optional — indexer falls back to Jupiter prices without it |
| `TELEGRAM_BOT_TOKEN` | from `.env`, if you've set up alerts | optional |
| `TELEGRAM_CHAT_ID` | from `.env`, if you've set up alerts | optional |

```bash
gh secret set AUTHORITY_KEYPAIR_JSON < ~/.config/solana/id.json
gh secret set PYTH_PRO_API_KEY --body "$(grep '^PYTH_PRO_API_KEY=' .env | cut -d= -f2-)"
```

### 3. Enable the workflows

They're active as soon as this commit lands on `main` — GitHub reads
`.github/workflows/*.yml` from the default branch automatically. Trigger a
manual run to check before waiting for the schedule:

```bash
gh workflow run score.yml
gh workflow run snapshot.yml
gh run watch
```

## What "unattended" actually means here

- **`score.yml`** pushes to devnet only. If it fails for an hour, the
  dashboard just shows slightly stale numbers — not silently wrong ones
  (the indexer's own no-exit-market cap and retry logic still apply).
- **`snapshot.yml`** commits to `main` directly with `[skip ci]`, so it
  doesn't loop-trigger other workflows. A missed run doesn't corrupt
  anything; the next scheduled run just picks up from wherever the market
  is then.
- **GitHub disables scheduled workflows on a repo with no activity for 60
  days.** The daily snapshot commits count as activity, so this is
  self-sustaining as long as at least one workflow succeeds periodically.
- **Scheduled-run timing isn't exact.** GitHub queues cron triggers and can
  delay them by minutes during high load. Don't rely on the snapshot
  landing at exactly 05:30/15:00 UTC — check `fetched_at` inside the
  snapshot's `sellable.json`, not the commit time.

## What this does *not* yet cover

- **Mainnet.** Both workflows target devnet. Moving to mainnet needs a
  funded, separate authority key and its own secret — don't reuse the
  devnet one.
- **Helius mint/burn webhooks.** Those need a server with a public URL to
  receive POSTs; GitHub Actions runners are ephemeral and have none. The
  `--once` scoring run still recomputes price, liquidity and the on-chain
  write every 15 minutes — it just doesn't react to mint/burn events
  in real time between runs.
- **The site's `lib/research.ts`.** Still generated by hand from a chosen
  snapshot. `latest.json` (written by every snapshot run) is there so this
  can be automated next, without redoing the collection logic.
